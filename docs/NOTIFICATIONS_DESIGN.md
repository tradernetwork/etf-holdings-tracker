# Watchlist notifications — backend v1

2026-10-10. Implemented but **off by default**. Anonymous Expo installations receive at most one logical digest per new market-day snapshot. No accounts, portfolio uploads, ads, or per-position push storms. This is a disclosure update, not a real-time trade feed.

## Signal contract and v1 scope

`api/notification_job.py:build_events` consumes `data.compute_daily_changes()`, which delegates to the guarded `_changes_between`. Significance is exactly `abs(activeWeightDelta) >= data._significance_threshold(fund)` (0.01 pp for broad funds, 0.02 otherwise). Never derive purchases from raw holding deltas. Price drift, split handling, junk exclusion and catch-up suppression stay owned by `api/data.py`.

A followed fund's significant equities produce opened/closed/added/trimmed notices. A followed ticker matches significant active-equity funds. Explicit follows of income funds can match their equity activity, labeled “overlay/collateral activity”; income collateral is excluded from ticker stock-conviction notifications. Matching both ticker and fund still produces one event. Both books must contain the fund, have parseable source dates, be non-stale, and have no carried-forward rows. Missing books cannot create exits. Catch-up funds get one informational notice **only when explicitly followed**, e.g. “ARKK has refreshed: changes since Sep 25 are not daily moves.” No fake gap-sized trade is sent.

`build_digest` freezes all matched events, shows up to three highlights plus an overflow count, and sends snapshot date and digest ID. Full events are available through the private digest endpoint. The initial native client will need to open that digest or a followed fund/ticker; the safe URL in the payload opens the public Holdings page. Empty results are recorded but produce no push.

Conviction crossings using the existing scorer, participant-change divergences using `_divergences_from`, and newly optionable/weekly listings using CBOE's real directory diff remain **future work**. They require prior-day state/baselines and explicit event preferences; v1 does not imply they shipped. Web Push/VAPID is deferred. A future Web transport can reuse device identities, follows, frozen digests, and the daily outbox, adding a separately validated subscription and delivery adapter; the worker and signal source remain shared.

## Persistence, authority, privacy

`api/notification_store.py` lazily creates `api/data/notifications.db`. Compose already mounts **`./api/data:/app/api/data` read-write**, separately from its read-only holdings CSV mount; no volume changes needed. WAL, foreign keys, short transactions and `BEGIN IMMEDIATE` coordinate the two API processes. SQLite files/WALs are already gitignored; DB permissions are 0600. Verify host ownership and backup/rebuild persistence before enablement (configuration and temporary-file persistence tested locally; no production deployment performed).

Tables: `devices` (UUID, SHA-256 hash of random 256-bit bearer secret, unique Expo token, timestamps), `follows` (unique device/kind/symbol), `source_runs` (day, input signature), `outbox` (unique device/day, frozen events/payload, attempts, lease, ticket/receipt status), `quotas` (transactional device counters), `enrollments` (hashed token/day anti-abuse counter). The bearer secret itself is returned once and never persisted server-side. Its entropy makes unsalted SHA-256 appropriate; possession authorizes only that installation. Registration never hands out an existing token owner's secret. Unauthenticated re-enrollment of the same token deletes the old installation and returns fresh credentials (reinstall recovery). Someone holding a victim's Expo token could reset that registration or choose different follows for fixed digest content; Expo tokens are not public, and this limited risk is accepted for v1. A SHA-256 token fingerprint/count is retained until the UTC-day boundary solely to enforce five unauthenticated enrollments/token/day; it survives device deletion, contains no token/follows, and is then purged. Authenticated token replacement cancels older in-flight/accepted work so an old receipt cannot prune the replacement. Identical token/follow updates do not cancel a pending digest.

Collect no email, advertising ID, location or portfolio. Tokens/watchlists are sensitive pseudonymous data; logs contain counts and safe error codes, never tokens/secrets/events. Outbox records expire after 30 days; unused device registrations after 180 days (management activity renews them). Deletion cascades through follows, outbox and device quotas; only the anonymous hashed token/day anti-abuse counter remains until the UTC-day boundary. Source-run rows contain no device data. Backups must expire within 30 days and privacy disclosures must explain delayed backup erasure and Expo/FCM processing. There is no “disable but retain server follows” endpoint in v1: unsubscribe deletes everything; local follows may remain on the phone.

## Client contract

Routes live at `/notifications`, with `include_in_schema=False`, outside the data-only public OpenAPI spec. Bodies/responses below match `mobile/lib/register-device.ts`. Except initial registration, send `Authorization: Bearer <secret>`; no device-ID header/query is needed.

| Request | Response / behavior |
|---|---|
| `POST /subscribe` with `{"transport":"expo","token":"ExponentPushToken[...]"}` (also supports `ExpoPushToken[...]`) | `{"deviceId":"UUID","secret":"random bearer"}`. New enrollment returns **201**. With existing bearer, replaces its token and returns the same credentials (**200**). Without bearer, an already-registered token deletes the old installation and creates fresh deviceId/secret (**201**); old secret becomes **401**. Authenticated replacement into a token owned by another installation gives **409**. |
| `GET /follows` | `{"follows":[{"kind":"fund","symbol":"ARKK"},{"kind":"ticker","symbol":"TSLA"}]}` sorted by kind/symbol. |
| `PUT /follows` with that same follows object | Atomically replaces up to 100 validated entries, uppercase normalization/deduplication; returns sorted follows. Unknown fund or invalid symbol gives **422**. Changed follows cancel unsent digests; there is no replacement push that day. |
| `DELETE /unsubscribe` or `DELETE /device` | `{"deleted":true}`; erases token/device/follows/outbox/quotas. Subsequent requests with the erased secret give **401**; client treats repeat-delete 401 as already removed. |
| `POST /test-push` (no body) | `{"queued":true,"digestId":"UUID"}`. Fixed message to own token only; sent by next sync job (normally within 15 min). |
| `GET /digests/{digestId}` | `{"snapshotDate":"2026-10-12","events":[...],"status":"accepted"}`; **404** if missing/not owned. Tickets mean acceptance; `delivered` means Expo's downstream receipt, not that a human saw it. |

All routes return **503** when `NOTIFICATIONS_ENABLED` is not `1`. Missing/invalid bearer: **401**. Invalid body: **422**. Exceeded quota: **429**. Provider errors happen asynchronously and are recorded in the outbox, never passed to the user as token-containing provider responses. Expo token strings are bounded and validated; no caller-supplied remote URL or push body.

Existing SlowAPI limits use the real IP passed through trusted proxy handling: subscribe 5/hour/IP plus 5/day/token for unauthenticated enrollments; follow reads 60/minute, writes 20/hour; deletes 30/hour; tests 10/hour/IP; private digests 60/minute. Counters remain per uvicorn worker. SQLite adds shared device quotas: follows 20/hour, authenticated token updates 10/hour, tests 3/day. Request authentication runs inside rate-limited handlers so invalid bearers also consume IP quotas. CORS permits PUT/DELETE and Authorization for the existing origin allowlist.

Mobile lifecycle is a separate Builder change: persist management credentials in native SecureStore, authenticate token re-registration, sync follow edits, delete remote registration when disabling/clearing, and handle 401/409/503. Backend and native flags stay off until both halves and a real EAS device are verified.

## Trigger, delivery and operational boundaries

`sync_data.sh` takes a host `flock` and invokes **`docker compose exec -T api python -m api.notification_job`** after a successful sync/health check, including the already-current path. A failed API rebuild now exits before the job; no Python runs on the host. The job no-ops immediately while disabled and starts no threads/timers in uvicorn. Running on the already-current path drains retry/test work and checks receipts; an entrypoint loop would duplicate jobs under two workers and obscure lifecycle.

`prepare_daily` selects market-day history, checks two input-file signatures around event preparation, and transactionally commits one `source_runs` entry and each device's unique daily outbox. Repeat syncs do not rebuild; registrations/follow additions after freeze wait for the next snapshot. Rewritten same-day CSVs never send a second digest. First enabled run may digest the current available market-day snapshot; it does not replay history. `source_runs` preserves signatures but v1 does not automatically publish correction alerts. Missing previous snapshot means no new digest, while old outbox/test delivery still proceeds.

The worker also holds a kernel lock in the writable state directory. `send_pending` uses durable 120-second claims, rechecks cancellation/token replacement before sending, drains up to 200 messages per sync, retries retryable transport/rate-limit failures with bounded exponential delays (900s–4h), at most five attempts, and expires unsent work after 24h. Conservative initial throughput: 200/day-digest deliveries every 15 minutes; raising this needs load/queue-age monitoring. A final micro-race with an external provider cannot undo a send already in progress when unsubscribe arrives. Acceptance followed by a crash before recording a ticket may duplicate delivery on retry: guarantee **one logical digest**, not exactly-once display.

`api/push_delivery.py` POSTs to fixed `https://exp.host/--/api/v2/push/send`, with optional `EXPO_ACCESS_TOKEN` bearer auth. Receipts use `/getReceipts`, up to 1,000 IDs/request, first checked after 15 minutes and marked missing after 24h. `DeviceNotRegistered` in either ticket or receipt prunes the device and its data. Other permanent errors stop that message; receipts are never retried as new pushes. HTTP 429/5xx/network failures retry within the bounded outbox policy. [Expo delivery contract](https://docs.expo.dev/push-notifications/sending-notifications/).

Set `NOTIFICATIONS_ENABLED=0` (default) and optional Expo access token in the host's gitignored `api/.env`, loaded by Compose `env_file`; rebuild/recreate as needed for environment changes. FCM credentials belong in Expo/EAS; never commit provider keys. SQLite/outbox uses existing box capacity; Expo's service is free but hosting, backup and operations remain costs. Expo has no delivery SLA. Test tickets/receipts, denial/revocation and installed release builds before enablement.

Play Store release still requires Android 13+ `POST_NOTIFICATIONS`, explicit opt-in, Android notification channel, and updated privacy/Data Safety disclosures. Existing native permission UI must remain usable when permission is denied. Future TWA Web Push depends on verified Digital Asset Links, browser support and a configured `TrustedWebActivityService` delegation service; a Bubblewrap shell alone is not proof notifications delegate correctly. Native v1 makes no TWA delivery claim.
